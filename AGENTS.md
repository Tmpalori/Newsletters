# Agent Instructions — The Vic 361

Read this file first if you are a coding agent (Codex, Claude Code, Cursor, etc.) about to make a change to this repo. It tells you how the system works, what you are and aren't allowed to touch, how to run the tests, and which invariants matter.

The companion files `CLAUDE.md` and `.cursorrules` redirect to this document so every agent flavor lands on the same source of truth.

## What this is

**The Vic 361** is a weekly community-events website for Victoria, TX (population ~65k). It collects events from public calendars and Apify-scraped Facebook/Instagram (OpenAI extracts events from posts and polishes descriptions) twice a week (Sunday and Wednesday afternoons); the site auto-publishes the new candidates when it redeploys, AI reviews free submissions and an event check hides obvious junk, and the owner steps in from the admin only for exceptions; the published list is served from Railway Postgres at [www.thevic361.com](https://www.thevic361.com).

- **Live site:** [www.thevic361.com](https://www.thevic361.com) — Railway (Express + Postgres)
- **Repo:** `Tmpalori/thevic361` (this repo)
- **Owner:** Tristen Palori ([tristen.m.palori@gmail.com](mailto:tristen.m.palori@gmail.com))

Production hosting:

- `www.thevic361.com` is a CNAME to `oln7ktx9.up.railway.app`. This is the canonical host (`SITE_URL`); always link to www.
- Apex `thevic361.com` resolves to Squarespace (domain forwarding), not Railway. It forwards `/path` to `www.thevic361.com//path`, which 404s, so only the bare homepage works on the apex. The Express apex → www redirect in `server/index.js` never sees apex traffic today.
- DNS is managed in Squarespace.
- Railway environments: `production`, `staging`, and PR-environments (auto-created per open PR, auto-destroyed on PR close). Each has its own forked Postgres.

## Source of truth — read this twice

| Layer | Role |
|---|---|
| **Railway Postgres `published_events.id=1`** | The **live** published list. The Express app serves `/events.json` from here. Written by: auto-publish (`server/autopublish.js`: on boot, `POST /api/admin/auto-publish`, and in `submissionsOnly` mode after an AI review approval), admin **Save & Publish** (`/api/admin/publish-events`), the event check's hide and the admin's restore (`server/eventcheck.js`), and `unpublishEvent` when an approved submission is un-approved (`server/submissionReview.js` / the Submissions tab). |
| **`docs/events.json`** | A **curated bundled fallback**, not authoritative. Only the admin Save & Publish flow may write it (and only when `GITHUB_TOKEN` is configured). The weekly collector workflow runs with `--candidates-only` and **must not** overwrite this file. |
| **`candidates.json`** | The full raw collector output, auto-published on the next boot. Auto-committed by the weekly workflow (Sunday and Wednesday). Safe to overwrite. |

Test `test_collect_events_safety.py` pins the `--candidates-only` invariant. **Do not break it.**

## Run, test, lint

### Node (server + frontend)

Node 22 LTS (`.nvmrc`, `engines`); CI and Railway use it. `package-lock.json` is committed: install with `npm ci`, and commit the lockfile with any dependency change.

```bash
npm ci
npm start          # node server/index.js — listens on $PORT or 3000
npm run dev        # alias to start (no nodemon configured)
npm test           # vitest run — runs every tests/*.test.js
```

### Python (collector + digest)

```bash
pip install -r requirements.txt
pip install -r requirements-dev.txt   # adds pytest

# Run the collector locally (writes candidates.json + ./events.json):
python collect_events.py --output ./docs/events.json --local-dir .

# CI-safe mode (does NOT touch docs/events.json):
python collect_events.py --candidates-only --output ./docs/events.json --local-dir .

# Run the test suite (tests live AT THE REPO ROOT, not under tests/):
pytest -q
```

`.github/workflows/tests.yml` runs both suites on every PR and on pushes to `main`. Run them locally before opening a PR too.

### Town settings (multi-city)

`server/town.js` holds what makes this site Victoria's: `townConfig(env, overrides)` returns `VICTORIA` (frozen, exactly today's values) when `TOWN` is unset or `victoria`, else `towns/<slug>/town.json` with the fields that follow from it (`siteUrl`, `emailFrom`, `icalDomain`, an empty `gaId`) derived from that town's own `domain` and `siteName`, never from Victoria's. Names, domains, the from-address, `siteUrl` and the GA ID are validated at boot (no `<`, `>`, `&`, `"` in names; a bad town stops the boot), so renderers interpolate them as is. `createApp` calls `useTown(townConfig(process.env, opts))` (`opts.town` takes a town.json-shaped object, for tests); `town` is a live binding, so read `town.siteName`, `town.domain`, `town.siteNameHtml`, `town.siteUrl`, `town.emailFrom`, `town.gaId`, `town.icalDomain`, `town.timezone` when rendering, never in a module-level constant (the advertise page's package points are getters for that reason; `gaSnippet()` replaced `GA_SNIPPET`). Dates, the scheduler's job slots, JSON-LD and `.ics` times and the Google Calendar link use `town.timezone` (`localDateStr`, `utcOffset`, which keeps half-hour zones' minutes, and `localParts` in `server/scheduler.js`; these were `chicagoOffset` and `centralParts`). `docs/app.js` and the Python side still say `America/Chicago` until steps 1.3c and 1.4. Fields arrive with the plan step that moves their literals (`MULTI_CITY_PLAN.md` 1.2). Key and idempotency prefixes (`vic361-…`), storage keys and `utm_source=thevic361` are not town fields yet and must not change for Victoria (Phase 2). `tests/town.test.js` renders a second town and checks no Victoria name, domain or GA ID leaks into its pages and emails.

Place names come from the town too: `townOf(ev)` falls back to `town.city`, schema.org addresses use `town.city` / `town.state`, event leads, `.ics` LOCATION and the Google Calendar location end in `, ${town.state}`, place labels and email footers use `town.cityState` ("Victoria, TX") and `areaServed` uses `town.cityStateLong` ("Victoria, Texas"), and `streetAddress` strips the town's own ", City, ST 12345" tail. The hub pages and seasonal guides (`HUB_PAGES`, `SEASONS`) and other sentences that say "Victoria" are page copy and move in plan step 1.2d. `tests/town_geography.test.js` checks a second town's pages, schema, calendar files, venue pages and email footers.

Page copy follows the town as well. `HUB_PAGES` and `SEASONS` keep their shape, but every title, h1, description and intro that names the place is a getter (`get title() { return `…${town.cityState}…`; }`), so write new copy that way, never as a plain string naming Victoria. A guide only one town has carries `only: '<town id>'` (Victoria's `/bach-festival` and `/tejas-fest`); `townSeasons()` is the town's list, used for routes and `activeSeasons` (nav, sitemap, llms.txt), so another town's guide gets no route. Sentences say `town.city`; the confirm and report email subjects say `town.shortName` ("Vic 361"); the about page's sources are `town.localSources` and llms.txt's "(the 361 area code)" is `town.areaCode` (empty: no line). The paid pick's name is `town.pickName` ("Vic’s Pick", curly, for pages and HTML email) and `town.pickNamePlain` ("Vic's Pick", for plain text and subjects); the package's name, CTA and blurb in `AD_PACKAGES` are getters, and the inbox's 💰 also matches the town's pick name. Only the words change: `/api/vics-pick/*`, `vic361_*` metadata and Stripe lookup keys stay as they are. The email header wordmark is built from `town.siteNameHtml` (text, plus a yellow badge for the `<span>` part). `docs/app.js` still says "Vic’s Pick" until step 1.3c. `tests/town_copy.test.js` runs a whole second-town app and checks no server-rendered page or email says Victoria or Vic 361 (the static homepage and `/submit` wait for step 1.3b).

Money and limits are `town.business` (Victoria: weekly sponsor 30000 cents, picks 4900/8900, 3/4 picks sold a day, 15/20 events and 2/3 editor's picks a day, a $25 monthly drawing plus $10 and $25 cards at 5 and 10 friends, subscriber count shown from 100). Another town's `town.json` overrides only what it sets. `VICS_PICK`, `DAY_MAX`, `PICKS` and `PICKS_MIN` keep their names as getter objects; `referralTiers()` replaced `REFERRAL_TIERS`/`DRAWING_AMOUNT`; the packages' `amount`, `price` and `limit` are getters, and every price shown (advertise page, checkout, submission emails) is generated with `dollars(cents)` from the same numbers Stripe charges. Stripe lookup keys still embed the amount (`vic361_<key>_<amount>`), so a price change makes a new Price as before. `docs/submit.html` and the admin still show Victoria's prices until step 1.3. `tests/town_business.test.js`.

Job times: `town.schedule` moves a job's start (`{ "newsletter": "07:13" }`, in the town's timezone) so several towns' sends and collects can be staggered; Victoria's is empty and runs `JOBS` as written. Days never move: every town's issues are Monday's and Thursday's, so that copy is shared. `startOf(job)` is the start the scheduler uses, `startLabel(name)` the "7:43 AM" the admin setup checklist shows, and `checkTownSchedule()` (run by `createApp` and `createScheduler`) stops the boot on an unknown job, a minute-interval job or a start after the job's cutoff. `tests/town_schedule.test.js`.

The static pages stay Victoria's: `docs/index.html` (the homepage template) and `docs/submit.html` keep Victoria's text. For another town `server/localize.js` `localizeHtml()` rewrites them through one table of Victoria's literals and the town's values (URL, name and header title, domain, GA ID or no Google tag at all, "Victoria, TX" and the city, pick name, pick prices, "in the 361" and the phone placeholder's area code), specific before general; for Victoria it returns the page untouched. The homepage template is localized when loaded (and the admin preview's raw page too); `/submit` gets a localized route only on another town's service, so Victoria's still comes from `express.static`. When you add Victoria-specific text to either page, add its literal to that table; `tests/town_static.test.js` fails if any of Victoria's name, domain, GA ID, prices or area code reaches another town's homepage or form. `docs/app.js` reads `window.__TOWN__` (`timezone`, `city`, `pickName`, `utmSource`), which `localizeHtml` injects before the app.js script tag on another town's pages only; with none it uses Victoria's values, so Victoria's page and behavior don't change. Its "today" is `townToday()` (exposed to tests as `__vic361App.today`). `town.utmSource` (Victoria `thevic361`; another town its domain without the TLD) is the `utm_source` on links we send people out through, server-side (`sponsorLinkUrl`, the sponsor redirect) and in app.js. `town.keyPrefix` (Victoria `vic361`; another town its slug, never `vic361`) starts every key the server hands an outside account: Stripe lookup keys, product metadata (`<prefix>_package`) and idempotency keys, Resend idempotency keys (newsletter batches, welcome, reminders, sponsor and submission mail) and Tremendous `external_id`s, so two towns on one account can't collide. Build such keys as `` `${town.keyPrefix}-…` ``, never with a literal `vic361`; `tests/town_keys.test.js` fails on one. Browser storage keys (`vic361-theme`, `vic361_admin_pat`…) stay as they are: each town has its own origin. Another town's checkout sessions (and their payment intents and subscriptions) carry `metadata.town`; Victoria's carry none, so its Stripe requests are unchanged. The webhook skips `checkout.session.*` and `customer.subscription.*` events tagged for another town (untagged = Victoria); invoices, charges and fraud warnings only ever match the town's own orders, and a fraud warning that matches none alerts only on Victoria. Inbound email (`server/inbound.js` `isForTown`): another town posts only mail sent (to or cc) to its own domain or a subdomain; Victoria posts everything except mail addressed only to another town's domain (`otherTownDomains()`, read from `towns/*/town.json`), so a Bcc or forward still reaches it. A town's data files come from `townPaths()` (`server/town.js`): Victoria's stay at the repo root (`candidates.json`, `collection_metadata.json`, `venues.json`…) and in `docs/` (`events.json`, `social/latest/`); another town's are under `towns/<slug>/`, its public ones in `towns/<slug>/public/`. The server reads them from there, `/api/config` gives the admin `github_events_path` and `github_candidates_path` for its GitHub reads and publishes, and `tests/town_paths.test.js` pins Victoria's. The Python twin is `town.py` `town_paths()` (plus `repo_path(key)`): the collector's `--candidates` and `--local-dir` defaults, the social kit's output and venues, `social_post.py`'s kit, `review_submissions.py`'s venues and `send_digest.py`'s candidates come from it. Workflows that touch these files run a `Town paths` step first (`python3 town.py paths >> "$GITHUB_ENV"`, giving `TOWN_DIR`, `TOWN_CANDIDATES`, `TOWN_EVENTS`, `TOWN_SOCIAL`…) and use those variables in their arguments and `git add`s; for Victoria they are exactly the old paths. `test_workflows.py` fails if a step reads `TOWN_*` before that step. The town workflows (collect, event check, digest, newsletter, social kit, submission review, uptime, Meta ads) take a `town` dispatch input (default `victoria`) and set `env: TOWN: ${{ inputs.town || 'victoria' }}`; scheduled runs are Victoria's. Another town's concurrency groups get a `-<slug>` suffix and its cache keys a `<slug>-` prefix (so Victoria's `review-state-` restore prefix can't match them); for Victoria both are empty, so its groups and keys are unchanged. Workflows the server starts (the scheduler's daily jobs, the admin's Run collect) get `townInputs()`: another town adds `town: <slug>`, Victoria's dispatches carry no `town` input, exactly as before. Another town starts no workflows at all (scheduler and Pull Now) until `TOWN_WORKFLOWS=1` (`townWorkflowsReady()`), to be set only once its GitHub Environment exists: before that its runs would use the repo-level settings, which are Victoria's. `town.py` `site_url()` also refuses another town on Victoria's URL, and `town.py paths` refuses a slug that isn't lowercase. `SLACK_TOWN_TAG` (Railway and the workflows' env) puts `[<tag>] ` before every Slack title, in `server/slack.js` `notify` (alerts too) and `scripts/slack_notify.py`, so towns can share channels; unset (Victoria) changes nothing. `GET /api/hq/summary` (`server/hq.js`) feeds the HQ dashboard: off (the site's own 404) unless `HQ_API_KEY` is set; then only `Authorization: Bearer <HQ_API_KEY>` gets in (an admin session doesn't, and the key opens no admin route). Counts and dates only (subscribers with 31 days of daily active counts and 30-day sign-up sources, last 4 issues, revenue with the last six months, 30-day ad spend and cost per subscriber, waiting submissions, upcoming events and last collect, health, which setup items are missing), rate limited (30/min) and cached 60 s. The admin Setup card and HQ share `setupReport()`. The owner inbox (`server/inbox.js`): `withInbox` wraps the app's Slack notifier so every `notify()` and `alert()` (alerts once per 15-minute key window) is also saved with a severity (urgent, today, fyi; `classify()` by channel and title emoji) to `inbox_events`, fire-and-forget and whether or not Slack is set up. `GET /api/hq/inbox?since=<id>` (same key, rate limit) returns them oldest first, 200 at a time, for HQ to tell Tristen through his assistant. Unlike the summary it carries names, emails and messages, so `forgetEmail` and the retention purge (contact-message cutoff) cover it. New owner pings land in the inbox automatically; give a new one a title whose emoji matches its severity, or extend `classify()` and `tests/inbox.test.js`. Anything broken must reach both Slack and the inbox (the owner's assistant reads it through HQ every 10 minutes): a save that fails (no store yet at boot, the database down) is kept, in order, and retried with the next save and every 2 minutes (`flushInbox`); a crash alert goes through the app's notifier once it's up, so it's saved too. The GitHub workflows' alerts come in through `POST /api/ops/report` (`server/opsReport.js`, `X-Ops-Secret`: `OPS_REPORT_SECRET`, else the `SUBMISSION_REVIEW_SECRET` chain): every step that posts to the alerts webhook also sets `OPS_REPORT_URL` and `OPS_REPORT_SECRET`, and `scripts/slack_notify.py` then sends the alert to the site, which saves it (a `⚠️` warning is `today`, `✅` fyi, the rest urgent) and posts it to Slack itself when the workflow couldn't (`test_workflows.py` pins every alert step). Workflow failure alerts also fire on `cancelled()` (a job timeout), except tests.yml. `/api/hq/inbox` also answers `latest` (the newest id) so HQ notices a reset database. When a site is down it can't write its own inbox: HQ (tristen-hq) turns failed pulls and its own checks of each town into inbox items. ## Collector quality

`merge_events` in `collect_events.py` is the single quality gate: it drops scraped events outside Victoria County (`out_of_area_reason`; local YAML and Google Sheet rows, `HAND_SOURCES`, are trusted and marked `curated`), moves street addresses out of the venue field and blanks placeholder venues like "Victoria" (with or without a ZIP: "Victoria, TX 77901") or "Restaurant of the Week" (`clean_venue`; a street with no `venues.json` match leaves the venue blank so the site shows the address), blanks a nightlife time that can't be right ("Comedy Night" at 10 AM), and fuzzy-dedupes per day (`is_same_event`: also ignores organiser prefixes and city words when both name one place, and treats Theatre Victoria as the Welder Center; AI-written post names of one festival day, like "Tejas Fest 2026 (Day 1)", "Tejasfest (VIP shift)" and "Tejas Fest - Main Stage", merge once the qualifiers are stripped, with a vague venue such as "Downtown Victoria" or "Main Stage" counting as unknown: `_same_festival`; one weekly special posted on FB and IG, like "Taco Tuesday - Birria Tacos" and "$2 Birria Taco Night", merges at one place when neither gives a time and the shared words, plurals folded, include a distinctive one, never just "Bingo" or "Trivia"), keeping the record from the higher-ranked source in `SOURCE_RANK` and filling gaps from the other. The merged name is the whole one over a cut-off copy, an official source's over an AI-written one, else the shorter. One listing each source words differently ("Wednesday Market", "Midweek Market" and "Victoria Farmers' Market", all 9 AM at the market) merges through `_same_slot`: the same venue name (not just a shared street address; never a vague venue), date and known start minute, at least one name AI-written, hand-entered or generic, and either a shared distinctive word (film/screening count as movie; weak words like "society" or "halloween" don't) or a generic name for the night's act ("Live Music", "Karaoke", "Trivia") of the same kind as anything generic in the other; two hand-entered events never merge this way. Auto-publish's `sameSlot` (`server/autopublish.js`) mirrors it for copies already live. A hand-entered event's price always wins: the AI review never changes `free` on a `curated`/`HAND_SOURCES` event (its free icon follows its own flag) and writes its description only when it's under `CURATED_REWRITE_BELOW_CHARS`, and `_merge_pair` keeps the hand-entered copy's `free`. ## Traffic stats

`server/analytics.js` powers the admin **Traffic** tab. People are counted from a `docs/track.js` beacon (`POST /api/track`: page views and sponsor/event/subscribe clicks; skipped in a browser signed into the admin). A page view is sent only once the visitor engages (scroll, tap, click or key) or the page has been visible for 5 seconds, so JS-running bots and instant bounces aren't counted; counts dropped when this started on 2026-10-05. search and AI crawlers are counted server-side by user agent (HTML pages plus `/events.json` and `/llms.txt`), at most 30 a minute per client address and 300 a minute overall (`crawlerMiddleware`; the user agent is unverified, so an uncapped loop could fill the database). AI bots are tagged `ask` (an assistant fetched the page to answer someone, e.g. ChatGPT-User), `search` or `training`; the summary's `ai` block reports people sent by AI referrers (or `utm_source`, which ChatGPT adds when there's no referrer) and those three counts. **Ad views:** paid placements carry `data-ad="<order id>"` (the weekly sponsor block and paid Vic's Picks, never editor's picks; `adAttr` in `server/seo.js`, the same in `docs/app.js`; `applyPlacements` puts `sponsor.order` and each paid pick's `sponsor_order` on the payload at read time, `/events.json` keeps them for app.js, Save & Publish strips `sponsor_order`). `track.js` sends one `{kind:'impression', ad}` per ad per page load once at least half of it has been on screen for 1 s with the tab in front (IntersectionObserver; no IO, no impressions), and clicks inside a `[data-ad]` carry `ad`; `beaconRow` takes only ids matching `AD_ID` and skips bots like views, and rows store it in the `ad` column. `/api/track` counts at most 20 impressions and 5 clicks per client address per ad (or per sponsor/event link) per day (`adBeaconAllowed`), so a script can't pad a sponsor report. The Traffic tab ignores impressions. Rows go to the `traffic` table (Postgres, ~400 days kept) with a daily salted visitor hash and no IPs or cookies. `GET /api/admin/traffic?days=N` returns the summary (Postgres groups rows in SQL and `summarize` weighs each by its count `n`, so a year's range stays cheap).

**Shares.** Every share button (`[data-share-url]`, `docs/track.js`) shares or copies the link with `?s=sh`, and counts a share (`share_native`, `share_from_list`) only once the share sheet reports it sent or the link is copied, not when the sheet is opened and closed. A page opened from such a link sends its view with `via: 'share'`, which `beaconRow` records as the source `Shared link` (`SHARED_LINK`, whatever app it was opened in), and the tag is removed from the address bar so a reload or copied URL doesn't count again. Vic's Pick reports add "Visits from shares" (`pickStats` `share_visits`/`share_people`). Admin Traffic → **Event stats** (`GET /api/admin/event-stats?week=<Monday>`, default last week; `eventWeekStats` in `server/sponsors.js`) lists every event dated that week, counting each from 7 days before its date through its date (`LEAD_IN_DAYS`), with page views (its own link taps and shares only, not those of the other events listed on its page), link taps, calendar adds, shares and visits from shares, plus the week's newsletter reach, and **Copy pitch** copies an email offering the venue a Vic's Pick.

**Meta ads.** Pages reached from links carrying a subscriber token (`/subscribe/confirm`, `/unsubscribe`) render with `layout({ pixel: false })`, which also leaves Google Analytics off, and the pixel script itself skips any URL with `token=`: both tools report page URLs to a third party. Everywhere else GA gets `page_location` as origin + path plus only `utm_*`/`gclid` (`GA_SNIPPET` in `server/seo.js`, copied into `docs/index.html` and `docs/submit.html`; a test keeps them identical). `/privacy` (`renderPrivacyPage` in `server/legal.js`, linked from every footer) discloses the pixel, Google Analytics (only for a town with a GA ID) and our own stats, as Meta's terms require. `/pixel.js` (`server/metaPixel.js`) loads the Meta Pixel on public pages when `META_PIXEL_ID` is set and is an empty script otherwise; it skips the same admin/preview/social-kit visits as `track.js`, and any browser sending Global Privacy Control (`navigator.globalPrivacyControl === true`; the privacy page promises this). It reports `PageView`, and `track.js` reports `Lead` when a newsletter signup succeeds. Ad links should end in `?utm_source={{site_source_name}}&utm_medium=paid&utm_campaign={{campaign.name}}`: a tap on an ad has the same facebook.com/instagram.com referrer as a free post, so `utm_medium=paid` is what puts it under **Meta ads** in the Traffic tab (`paidSource` in `server/analytics.js`; other paid sources show as **Other ads**).

## Auto-publish

`server/autopublish.js`: each collector run commits `candidates.json`, which redeploys the site; on boot in production (`RAILWAY_ENVIRONMENT_NAME=production`, unless `AUTO_PUBLISH=0`) the upcoming candidates plus approved submissions are published to the store. Upcoming events already published are kept; one it added takes the collector's newer copy of itself (time, venue, address, link, description, icons; the name only when the live one was cut off), unless the admin edited it, it's an approved submission or featured, and a hidden one keeps its name and venue (its key); `auto_publish.keys` follows the new key (`AUTO_PUBLISH_RULES` 3). An event it added is taken down only after two collector runs in a row miss it (`auto_publish.missing`, counted once per `last_updated`), each with all of its sources `ok` in `candidates.json`'s `sources` map (`partial` doesn't count: an AllEvents page came back full (`ALLEVENTS_PAGE_CAP`; the "all" page is a capped trending list) or failed, a library week, city calendar or chamber detail page, or J Welch date page failed, one FB-events actor was down, or an FB-events/Eventbrite search hit its result cap, via `_mark_partial`), and never when it came from FB/IG posts (`NEVER_RETIRE_SOURCES`; window-limited; each key's sources are kept in `auto_publish.sources`; a Gemini-only event retires like any other, since Gemini's answer was its only evidence), nor when the run looks broken. Approved submissions (also in `keys`) count as found while their row is approved, since the collector never lists them (read with `store.list({ status: 'approved', fromDate: today })`, which has no row cap: the admin list's newest-500 cap once dropped an approval made long before its date, and it was retired as missing; `retryLive`, the paid pick reminders and the admin picker read it the same way); when the approved list can't be read, nothing is retired. Events it added that the admin later removed are remembered (`auto_publish` in the published payload, hidden from `/events.json`) and not re-added, nor is a collector copy that `sameEvent` matches with a removed or hidden key (the AI's names drift run to run; an approved submission is never blocked this way). A collector copy that only `sameSlot` matches with a live event folds into it without refreshing it. An approved submission that merged into a listed event under another name is recorded in `auto_publish.aliases` (submission key → live key); when that live event is removed, the alias counts as removed too, so the submission's copy doesn't come back. `POST /api/admin/auto-publish` forces a run. The collector drops non-events (`non_event_reason`: job/internship posts, booking ads, awareness-day posts) and decodes HTML entities; with `OPENAI_API_KEY`, the AI review also returns `keep: false` for non-events. `weekly-collect.yml` runs Sunday and Wednesday. Whether a published event is still upcoming is decided on its edited copy (the `event_edits` overlay), so an event the admin re-dated to later stays live past its stored date without a Save & Publish; when the edits can't be read, past events stay that run too. This week's earlier days (from Monday, the collector's `backfill_to_monday` window) stay published and fill in from the collector, so the week view never shows past days empty; only events still to come are refreshed, counted for the health check or retired, and removals are remembered through the week (`AUTO_PUBLISH_RULES` 8). Every read-modify-write of the published payload (auto-publish in both modes, Save & Publish, `unpublishEvent`/`replacePublishedEvent`/`forgetRemoved`, keep-event, the event check's hide/restore, the edit's kept-key move) runs under `withPublishedLock` (`server/db.js`), an in-process queue, so two writers can't undo each other; a writer must not call another writer inside it.

## Growth (admin)

`server/growth.js` is Admin → Growth, and its two goal bars are also at the top of Home. `GET /api/admin/growth?days=7|30|90` (admin only) returns:
- **goals:** active subscribers against `SUBSCRIBER_GOAL` (10,000), with the pace (net subscribers per day over the last 14 days) and the date the list reaches the goal at that pace; this Central month's sponsor revenue (`monthRevenue`: orders paid this month that weren't refunded, plus monthly venue partners still active from an earlier month) against `REVENUE_GOAL_CENTS` ($10,000).

It answers with its own count for yesterday and the last 7 days, and the Slack report adds a "✅ Real, from the site" line with them. A failed post is a `::warning::`, and the report goes out anyway.

Then one OpenAI call (`OPENAI_MODEL`, default gpt-5-mini) over the whole list for what per-event checks can't see, like the same event at two venues; skipped without `OPENAI_API_KEY`. Rule findings it's sure about (church/worship events by name or venue, non-events, exact duplicates, the library's copy of a program the city calendar lists at its real place with the same hours, and a cut-off name when the same event's full listing is at the same place that day: its name holds every word left in the cut-off one, or after an "Organizer — " prefix, or it starts at the same known time and shares a distinctive word; another event at the venue isn't enough, and a vague venue ("Victoria", "Downtown") never counts as a place; `AUTO_HIDE`) it hides through `POST /api/event-check/hide` (`server/eventcheck.js`, `X-Cron-Secret` = `EVENT_CHECK_SECRET`, falling back to `NEWSLETTER_CRON_SECRET`; at most 10 per run, only live upcoming events). An approved community submission (`submitted: true`) is never auto-hidden either (nor picked as the copy to hide for a duplicate): the owner approved it by hand, often over the same rule, so it's only reported. Duplicates are only hidden when exact (same normalized name, venue and start) and neither copy is featured; the copy with less detail goes, fuzzy matches are only reported. Hiding never deletes: the published payload gains a `hidden` entry, matched by the event's original key (date|name|venue before the edits overlay), not its page URL, so slug renumbering and admin renames can't move or undo it; entries are kept 400 days so past pages stay hidden, and `getPublicPayload` (and the bundled fallback) leave those events out (site, `/events.json`, newsletter, social kit, sitemap, event pages); auto-publish and Save & Publish carry it forward. ## Scheduler

GitHub cron runs hours late on this repo, so the always-on server is the clock (`server/scheduler.js`, production only, `SCHEDULER=0` turns it off). In Central time, DST-correct: Sunday and Wednesday 3:23 PM dispatch `weekly-collect.yml` (`weekly-collect`, `weekly-collect-midweek`, until 9 PM; GitHub skipped the Sunday cron on Oct 4 and Oct 11, 2026), Monday 6:43 AM (and Thursday 6:00 AM, `event-check-weekend`, before the weekend issue) dispatches `event-check.yml`, Monday 7:43 AM sends the newsletter in-process (`scheduledSend`, retried after 5, 15 and 30 minutes, then an alert), Thursday 7:00 AM the weekend issue the same way (`newsletter-weekend`, `scheduledSend('weekend')`), daily 8:37 AM `meta-ads.yml` and 8:47 AM `social-kit.yml` (both with the `scheduled=true` input, so they behave like the cron), daily 9:00 AM `sponsors.sendSponsorReports(now)` when it exists, daily 3:17 AM `privacy-purge` (`server/privacy.js`: clears the IP address and user agent on submissions older than 12 months, deletes contact messages older than 24 months), every 15 minutes `submission-review.yml`, and hourly an in-process site check (database, at least 10 upcoming events, a collect within 8 days, and each Sunday/Wednesday collect in by 3 hours after its slot (`missedCollect`, against `auto_publish.from`); alerts once a day while it lasts, a note when it clears; alerts go to Slack #alerts and, as urgent, the owner inbox HQ reads). Each daily/weekly job is claimed once per slot in `scheduler_runs` (one SQL statement, so a restart or overlapping deploy containers can't double-fire); a job missed while the server was down runs later the same day. Dispatch needs `GITHUB_TOKEN` with Actions: write; without it the dispatch jobs are left to GitHub's cron, and a refused token (401/403) alerts once a week and shows on the setup checklist. The GitHub crons stay as fallbacks: each of social kit, event check, ads report and newsletter lists its slot at both its CDT and its CST UTC time, and its `gate` job keeps only the cron matching Central's current offset (`TZ=America/Chicago date +%z`), then asks `GET /api/scheduler/ran?job=…` and skips when the site already ran that slot. (One cron pinned to CDT fired an hour early all winter: `ran` still answered for the previous slot, and the newsletter could go out before the event check.) Weekly Collect's fallback keeps its single `23 20` UTC crons: its `towns` job asks each scheduled town's site `ran?job=weekly-collect` (or `-midweek` for the Wednesday cron), looks once more after 2 minutes, and drops the towns that already started; in winter the cron fires before 3:23 PM, when `ran` still answers for the last slot, so it stands down and the site's run covers it. Submission review is idempotent. `newsletter.yml` retries 4 times. The one newsletter switch is the Railway variable `NEWSLETTER_AUTOSEND` (on unless `0`); the cron endpoint honors it for runs marked `X-Cron-Scheduled: 1`. Tests: `tests/scheduler.test.js`, `tests/ops.test.js`.

The server's own hourly check (`server/scheduler.js`) also alerts when fewer than 10 upcoming events are live or the last collect is over 8 days old (`collected_at`). It also alerts (`subscribers`) when the newsletter has 0 active subscribers while the last `newsletter_sends` row had recipients, and `ready()` alerts `db-fresh` in production when it had to create the `subscribers` or `sponsor_orders` table (a new, empty database); see Backups.


`server/slack.js` posts to a Slack incoming webhook (`SLACK_WEBHOOK_URL`, same setup as austincommercialsites.com). No-op when unset. Server pings: new event submission, sponsor paid, venue partner cancelled or payment failing, newsletter sent (or partly failed / skipped because nothing was published), and alerts for 500s (keyed on the error message; 4xx client errors like malformed JSON or a bad `%` escape answer with their status and never alert), Stripe checkout or webhook failures, crashes, boot failures, a database unreachable at boot (the server still starts: pages fall back to the bundled `docs/events.json` and the store retries on the next query; the pg pool has an `error` listener, a 5 s connect timeout and 15 s query/statement timeouts) and a flood of failed admin sign-ins. Alerts are de-duplicated per key for 15 minutes. Slack posts and the Turnstile check time out after 8 s, so a hung Slack or Cloudflare can't freeze a form. Five channels, each optional and falling back to `SLACK_WEBHOOK_URL`: `SLACK_SALES_WEBHOOK_URL` (refunds, disputes, failed payments, sponsor and pick reports, a paid pick marked rejected), `SLACK_ACTIVITY_WEBHOOK_URL` (submissions, auto-publish, newsletter sent), `SLACK_ALERTS_WEBHOOK_URL` (every `alert()`), `SLACK_HYPE_WEBHOOK_URL` (wins only: new subscribers, new paid sponsors and Vic's Picks; falls back to sales) and `SLACK_INBOX_WEBHOOK_URL` (people talking to us: email replies to news@, contact-form messages, and each "Replied to" we send; falls back to activity). Pass `channel` to `slack.notify` for new pings. A refused webhook (HTTP 403/404/410, or `no_service`, `channel_is_archived` and the like: archived channel, removed app) is remembered per channel by `server/slack.js` (`slack.refused()`), fails the Slack item in the admin setup checklist and is a problem in the hourly site check; it clears on the next post that goes through. GitHub Actions use `scripts/slack_notify.py`, which exits 2 with an `::error::` on a refused webhook (so the run goes red and GitHub emails the owner) and 0 on a hiccup (timeout, 5xx); failure steps read `SLACK_ALERTS_WEBHOOK_URL`, the collect-done and outreach steps read `SLACK_ACTIVITY_WEBHOOK_URL`, both falling back to `SLACK_WEBHOOK_URL`: weekly collect done (candidate count plus the collector's warnings from `collection_metadata.json`, also sent to the alerts channel) or failed, social kit / newsletter / digest failures, tests failing on main, and `uptime.yml` (site check every 5 minutes: alerts once when down, hourly while down, once when back; also a phone push when the `NTFY_TOPIC` secret is set; daily stale-feed check). Async route handlers are wrapped (`catchAsyncRoutes` in `server/index.js`) so a rejected store call answers 500 instead of hanging on Express 4. Auto-publish alerts when a run finds far fewer events than the last (nothing retired), when nothing upcoming is published, and when it can't run on boot.

## Backups

Postgres on Railway holds the only copy of subscribers, sponsor orders, submissions, admin edits, the hidden/kept/rejected state and the event archive; events refill from `candidates.json`, nothing else does. The admin's Email tab can download the subscriber list as CSV (`GET /api/admin/subscribers.csv`), and RAILWAY.md "Backups and data exports" has an encrypted `pg_dump` recipe (never a GitHub Actions artifact: the repo is public). The repo has no backup job, so **the owner must turn on Railway's scheduled Postgres backups** (Railway dashboard → the Postgres service → Backups → enable a daily schedule; keep at least 7 days) and check after a week that backups are listed.

To restore: Postgres service → Backups → pick the latest backup from before the loss → Restore (Railway restores into the service's volume and restarts it). If the service was recreated instead, restore the backup to it, then make sure the app's `DATABASE_URL` references that service, and redeploy the app. Afterwards check admin Home (subscriber count), the Sponsors tab and `/api/health?deep=1`. The server alerts `db-fresh` when production boots on a database without the `subscribers` or `sponsor_orders` table, and the hourly check alerts when active subscribers drop to 0 after an issue went out; either one means restore before the Monday newsletter.

## Conventions

- **Python:** stdlib + `requests` + `beautifulsoup4` + `pyyaml`. No Django, no FastAPI, no async — keep `collect_events.py` blocking and simple.
- **JavaScript:** ES modules (`"type": "module"` in `package.json`). No TypeScript. No bundler — `docs/*.js` is loaded as-is by the browser.
- **No new dependencies without strong justification.** This is a twice-weekly cron job + a small Express app. Every dependency is a collect-day failure mode.
- **Comments explain *why*, not *what*.** The existing code does this consistently — match it. Documenting the rationale is half the value of every PR.
- **Errors include `.status` when they wrap an HTTP response** (see `server/github.js`) so route handlers can branch on it.
- **Outbound HTTP has a deadline.** Turnstile and Slack use 8 s, Resend (`server/newsletter.js`) and the GitHub API (`server/github.js`, `GITHUB_TIMEOUT_MS`; a timeout throws an Error with `code: 'timeout'` and no `.status`, so the callers' local-file fallbacks run) 15 s. Pass `signal: AbortSignal.timeout(ms)` to any new `fetch`.
- **Secrets only via env vars.** Never commit `.env`. `requirements.txt` caps each package below its next major version; raise a cap deliberately, with a test run.

## Don't-touch list

These files / behaviors are load-bearing and **must not change** in a normal PR. If you genuinely need to change one, call it out explicitly in the PR description and assume it needs human review.

1. **`docs/events.json` outside the admin Save & Publish flow.** The weekly workflow uses `--candidates-only` for a reason. `test_collect_events_safety.py` pins this.
2. **`candidates.json`** in a feature PR — it's a runtime artifact written by the weekly workflow.
3. **`collection_metadata.json`** in a feature PR — same, runtime artifact.
4. **`.last-published-digest-*` files** — markers from the decommissioned reply-to-email approval flow. Leave alone.
5. **The `weekly-collect.yml` cron expressions `23 20 * * 0` and `23 20 * * 3`.** The 1-hour DST drift is intentional and documented in the workflow header. Do not "fix" it. (Moved from `0 23` in Oct 2026 at the owner's request, because GitHub started the on-the-hour evening slot 45–90 min late; keep `server/sources.js` in sync if it ever changes; `tests/sources.test.js` checks they match.)
6. **Step / job timeouts in `weekly-collect.yml`.** Each value is justified by a specific run ID in the comments. Don't lower without strong reason.
7. **The `--candidates-only` flag default behavior.** Default is *off* (so local runs still write `events.json`); CI explicitly sets it.
8. **`server/auth.js` — the HMAC-SHA256 token format.** Single algorithm, no `alg` header. Do not switch to a JWT lib.
9. **The legacy `ADMIN_TOKEN` fallback path.** Documented in `index.js`. Keep working.
10. **The browser-side GitHub PAT path in `docs/admin.js`.** Intentional bypass for when server-side `GITHUB_TOKEN` isn't configured. When the server has admin login on, a leftover PAT in localStorage is ignored and an expired session shows the sign-in form. Only a 401 whose `error` is a session error signs the admin out; `/api/admin/trigger-collect` answers 502 `github-token-invalid` for a bad server token.

## Security notes

- **Cron secrets.** `NEWSLETTER_CRON_SECRET` (send the newsletter), `EVENT_CHECK_SECRET` (hide live events) and `SUBMISSION_REVIEW_SECRET` (approve and publish submissions) are meant to differ. For older setups the server and workflows fall back `SUBMISSION_REVIEW_SECRET` → `EVENT_CHECK_SECRET` → `NEWSLETTER_CRON_SECRET`, so with only one set, that one value grants all three. Keep the fallbacks (removing them would break a running setup), but the admin setup checklist flags a shared value ("Each automation has its own secret").
- **CSP.** `/admin.html` gets `script-src 'self'` plus a hash of its inline theme snippet (computed at boot from the file), because its session token lives in localStorage. Public pages have no `script-src`: they use inline scripts, inline `onload`/`onclick` handlers, GA, the Meta Pixel and Turnstile, so one would need nonces first. Don't add a third-party or inline script to `admin.html` without checking the CSP. The admin CSP is chosen on the decoded, normalized path and again by the file `express.static` serves, so `/admin%2Ehtml` or `/%61dmin.html` can't load the page under the public CSP. `X-Powered-By` is off.
- `trust proxy` is `1` (Railway's edge is the single hop). Don't set it to `true`: Express would then take the client-supplied left-most X-Forwarded-For entry as `req.ip`, and every per-IP rate limit could be bypassed.
- Every rate limiter keys a client address through `ipKey` (IPv6 on its /64; `createRateLimiter` does it for any key that is an IP, so the contact, newsletter and sponsor forms get it too). Admin sign-in: 10 login attempts per client per 15 minutes; wrong legacy `ADMIN_TOKEN` guesses are capped at 20 per client; and 100 failures (logins plus wrong tokens) across all clients send one Slack alert (alert only: blocking everyone would lock the owner out too).
- Submission dates must round-trip (`2026-11-31` is rejected, not rolled to Dec 1), and the public form's submitter email must also pass the newsletter's `normalizeEmail` (Resend refuses `bob@gmail.com.`). The admin edit form's date is `type=date`, and typed-but-unsaved edit fields survive re-renders (`state.drafts`). The public form's start times run from 5:00 AM.
- Anything rendered into HTML attributes must escape quotes (`escHtml` in both `server/seo.js` and `docs/app.js` does). `safeUrl` / `safeHref` reject URLs containing whitespace, quotes or angle brackets.
- Use function replacements (`.replace(x, () => html)`) when inserting rendered content: event text can contain `$'` / `$&`.
- Weekly sponsor holds are saved before the Stripe call, under an in-process lock; a payment for an already-sold week is marked `conflict` and flagged in Slack for a refund. Open (unpaid) holds are capped: one per email, and at most `MAX_HOLDS_PER_CLIENT` (3) per network address (`holdClient`, a salted hash of `ipKey`, stored as the order's `client`), since a mobile carrier or office puts many real buyers behind one address; a checkout past the cap releases that address's oldest hold, so one visitor can't hold every week and pick slot.
- Admin secrets: `ADMIN_SESSION_SECRET` / `ADMIN_TOKEN` under 32 characters (random keys nobody types) fail the required "Admin session secret and token are long enough" setup check and alert Slack on every production boot. `ADMIN_PASSWORD` under 12 is the owner's call: only the recommended "Admin password is 12+ characters" setup item, no alert or log line (the owner chose to keep theirs). Not a boot failure, on purpose: the live site may run on them and refusing to start would take it down.
- Personal data: `server/privacy.js` (daily retention purge, admin "Delete their data" = `POST /api/admin/privacy/forget`, subscriber CSV export). Forgetting an address deletes the subscriber and their opens, contact messages and the submitter fields on their submissions, and masks the address (`j•••@gmail.com`) on sponsor orders and referral rewards; the mailer never sends to a masked address.
- Public forms (submit, newsletter signup and the homepage card, contact, sponsor checkout) carry a hidden spam-trap field, `hp_field` (`server/honeypot.js`, `display:none`). It was `company`, which browsers autofill for business owners, silently dropping real submissions and checkouts; the old name is still honored for cached pages. A hit answers as if it worked, is logged, and Slack's activity channel hears about it at most once a day per form, with the count.
- Cloudflare Turnstile (`TURNSTILE_SITE_KEY` / `TURNSTILE_SECRET_KEY`) protects `/api/submissions`, `/contact`, `/api/subscribe` and `/advertise/checkout`. `docs/turnstile.js` mounts an interaction-only widget on forms marked `data-turnstile` (loaded on first focus; `data-turnstile="fetch"` forms call `vicTurnstile.token(form)`); the server checks `cf-turnstile-response` or `turnstile_token` via `verifyHuman` in `server/index.js`, and when Cloudflare reports the hostname a token was solved on, it must be the site's (apex or www, plus `RAILWAY_PUBLIC_DOMAIN`), so a widget shared with another site can't pass tokens from there. Both off until the keys are set.
