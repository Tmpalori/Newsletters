# Agent Instructions — The Vic 361

Read this file first if you are a coding agent (Codex, Claude Code, Cursor, etc.) about to make a change to this repo. It tells you how the system works, what you are and aren't allowed to touch, how to run the tests, and which invariants matter.

The companion files `CLAUDE.md` and `.cursorrules` redirect to this document so every agent flavor lands on the same source of truth.

## What this is

**The Vic 361** is a weekly community-events website for Victoria, TX (population ~65k). It collects events from public calendars and Apify-scraped Facebook/Instagram (OpenAI extracts events from posts and polishes descriptions) twice a week (Sunday and Wednesday afternoons); the site auto-publishes the new candidates when it redeploys, AI reviews free submissions and an event check hides obvious junk, and the owner steps in from the admin only for exceptions; the published list is served from Railway Postgres at [www.thevic361.com](https://www.thevic361.com).

- **Live site:** [www.thevic361.com](https://www.thevic361.com) — Railway (Express + Postgres)
- **Repo:** `Tmpalori/Newsletters` (this repo; it was `Tmpalori/thevic361`, and GitHub still redirects the old name). One codebase for every town.
- **Owner:** Tristen Palori ([tristen.m.palori@gmail.com](mailto:tristen.m.palori@gmail.com))

Production hosting:

- `www.thevic361.com` is a CNAME to `oln7ktx9.up.railway.app`. This is the canonical host (`SITE_URL`); always link to www.
- Apex `thevic361.com` resolves to Squarespace (domain forwarding), not Railway. It forwards `/path` to `www.thevic361.com//path`, which the server collapses to `/path` with a 301, but the forwarding drops the query string (so `?ref=` is lost on the apex). The Express apex → www redirect in `server/index.js` never sees apex traffic today.
- DNS is managed in Squarespace.
- Railway: one project, **Newsletters**, holds every town's web service, jobs service and Postgres. Environments: `production` (every town) and `staging` (Victoria's only, with its own forked Postgres). PR environments are off for the project (RAILWAY.md "New town on Railway"): a PR would copy every town and its database.

## Source of truth — read this twice

| Layer | Role |
|---|---|
| **Railway Postgres `published_events.id=1`** | The **live** published list. The Express app serves `/events.json` from here. Written by: auto-publish (`server/autopublish.js`: on boot, `POST /api/admin/auto-publish`, and in `submissionsOnly` mode after an AI review approval), admin **Save & Publish** (`/api/admin/publish-events`), the event check's hide and the admin's restore (`server/eventcheck.js`), and `unpublishEvent` when an approved submission is un-approved (`server/submissionReview.js` / the Submissions tab). |
| **`docs/events.json`** | A **frozen bundled fallback** (Victoria's), not authoritative: served only when her database has nothing published. Nothing writes it in production any more (Save & Publish commits it only on a service without jobs on Railway that has a `GITHUB_TOKEN`). The collector runs with `--candidates-only` and **must not** overwrite this file. |
| **`candidates.json`** | The raw collector output. The jobs worker hands each collect's copy to the site (`town_files`), which auto-publishes it at once; the file in git is Victoria's old copy, used only when it's newer than the database's. Safe to overwrite. |

Test `test_collect_events_safety.py` pins the `--candidates-only` invariant. **Do not break it.**

## Run, test, lint

### Node (server + frontend)

Node 22 LTS (`.nvmrc`, `engines`); CI and Railway use it. `package-lock.json` is committed: install with `npm ci`, and commit the lockfile with any dependency change.

```bash
npm ci
npm start          # node server/index.js — listens on $PORT or 3000
npm run dev        # alias to start (no nodemon configured)
npm test           # vitest run — runs every tests/*.test.js
```

### Python (collector + digest)

```bash
pip install -r requirements.txt
pip install -r requirements-dev.txt   # adds pytest

# Run the collector locally (writes candidates.json + ./events.json):
python collect_events.py --output ./docs/events.json --local-dir .

# CI-safe mode (does NOT touch docs/events.json):
python collect_events.py --candidates-only --output ./docs/events.json --local-dir .

# Run the test suite (tests live AT THE REPO ROOT, not under tests/):
pytest -q
```

`.github/workflows/tests.yml` runs both suites on every PR and on pushes to `main`. Run them locally before opening a PR too.

### Town settings (multi-city)

`server/town.js` holds what makes this site Victoria's: `townConfig(env, overrides)` returns `VICTORIA` (frozen, exactly today's values) when `TOWN` is unset or `victoria`, else `towns/<slug>/town.json` with the fields that follow from it (`siteUrl`, `emailFrom`, `icalDomain`, an empty `gaId`) derived from that town's own `domain` and `siteName`, never from Victoria's. Names, domains, the from-address, `siteUrl` and the GA ID are validated at boot (no `<`, `>`, `&`, `"` in names; a bad town stops the boot), so renderers interpolate them as is. `createApp` calls `useTown(townConfig(process.env, opts))` (`opts.town` takes a town.json-shaped object, for tests); `town` is a live binding, so read `town.siteName`, `town.domain`, `town.siteNameHtml`, `town.siteUrl`, `town.emailFrom`, `town.gaId`, `town.icalDomain`, `town.timezone` when rendering, never in a module-level constant (the advertise page's package points are getters for that reason; `gaSnippet()` replaced `GA_SNIPPET`). Dates, the scheduler's job slots, JSON-LD and `.ics` times and the Google Calendar link use `town.timezone` (`localDateStr`, `utcOffset`, which keeps half-hour zones' minutes, and `localParts` in `server/scheduler.js`; these were `chicagoOffset` and `centralParts`). `docs/app.js` and the Python side still say `America/Chicago` until steps 1.3c and 1.4. Fields arrive with the plan step that moves their literals (`MULTI_CITY_PLAN.md` 1.2). Key and idempotency prefixes (`vic361-…`), storage keys and `utm_source=thevic361` are not town fields yet and must not change for Victoria (Phase 2). `tests/town.test.js` renders a second town and checks no Victoria name, domain or GA ID leaks into its pages and emails.

Place names come from the town too: `townOf(ev)` falls back to `town.city`, schema.org addresses use `town.city` / `town.state`, event leads, `.ics` LOCATION and the Google Calendar location end in `, ${town.state}`, place labels and email footers use `town.cityState` ("Victoria, TX") and `areaServed` uses `town.cityStateLong` ("Victoria, Texas"), and `streetAddress` strips the town's own ", City, ST 12345" tail. The hub pages and seasonal guides (`HUB_PAGES`, `SEASONS`) and other sentences that say "Victoria" are page copy and move in plan step 1.2d. `tests/town_geography.test.js` checks a second town's pages, schema, calendar files, venue pages and email footers.

Page copy follows the town as well. `HUB_PAGES` and `SEASONS` keep their shape, but every title, h1, description and intro that names the place is a getter (`get title() { return `…${town.cityState}…`; }`), so write new copy that way, never as a plain string naming Victoria. A guide only one town has carries `only: '<town id>'` (Victoria's `/bach-festival` and `/tejas-fest`); `townSeasons()` is the town's list, used for routes and `activeSeasons` (nav, sitemap, llms.txt), so another town's guide gets no route. Sentences say `town.city`; the confirm and report email subjects say `town.shortName` ("Vic 361"); the about page's sources are `town.localSources` and llms.txt's "(the 361 area code)" is `town.areaCode` (empty: no line). The paid pick's name is `town.pickName` ("Vic’s Pick", curly, for pages and HTML email) and `town.pickNamePlain` ("Vic's Pick", for plain text and subjects); the package's name, CTA and blurb in `AD_PACKAGES` are getters, and the inbox's 💰 also matches the town's pick name. Only the words change: `/api/vics-pick/*`, `vic361_*` metadata and Stripe lookup keys stay as they are. The email header wordmark is built from `town.siteNameHtml` (text, plus a yellow badge for the `<span>` part). `docs/app.js` still says "Vic’s Pick" until step 1.3c. `tests/town_copy.test.js` runs a whole second-town app and checks no server-rendered page or email says Victoria or Vic 361 (the static homepage and `/submit` wait for step 1.3b).

Money and limits are `town.business` (Victoria: weekly sponsor 14900 cents, picks 2900/3900, 3/4 picks sold a day, 15/20 events and 2/3 editor's picks a day, a $25 monthly drawing plus $10 and $25 cards at 5 and 10 friends, subscriber count shown from 100). Another town's `town.json` overrides only what it sets. `VICS_PICK`, `DAY_MAX`, `PICKS` and `PICKS_MIN` keep their names as getter objects; `referralTiers()` replaced `REFERRAL_TIERS`/`DRAWING_AMOUNT`; the packages' `amount`, `price` and `limit` are getters, and every price shown (advertise page, checkout, submission emails) is generated with `dollars(cents)` from the same numbers Stripe charges. Stripe lookup keys still embed the amount (`vic361_<key>_<amount>`), so a price change makes a new Price as before. `docs/submit.html` and the admin still show Victoria's prices until step 1.3. `tests/town_business.test.js`.

Job times: `town.schedule` moves a job's start (`{ "newsletter": "07:13" }`, in the town's timezone) so several towns' sends and collects can be staggered; Victoria's is empty and runs `JOBS` as written. Days never move: every town's issues are Monday's and Thursday's, so that copy is shared. `startOf(job)` is the start the scheduler uses, `startLabel(name)` the "7:43 AM" the admin setup checklist shows, and `checkTownSchedule()` (run by `createApp` and `createScheduler`) stops the boot on an unknown job, a minute-interval job or a start after the job's cutoff. `tests/town_schedule.test.js`.

The static pages stay Victoria's: `docs/index.html` (the homepage template) and `docs/submit.html` keep Victoria's text. For another town `server/localize.js` `localizeHtml()` rewrites them through one table of Victoria's literals and the town's values (URL, name and header title, domain, GA ID or no Google tag at all, "Victoria, TX" and the city, pick name, pick prices, "in the 361" and the phone placeholder's area code), specific before general; for Victoria it returns the page untouched. The homepage template is localized when loaded (and the admin preview's raw page too); `/submit` gets a localized route only on another town's service, so Victoria's still comes from `express.static`. Its "today" is `townToday()` (exposed to tests as `__vic361App.today`). `town.utmSource` (Victoria `thevic361`; another town its domain without the TLD) is the `utm_source` on links we send people out through, server-side (`sponsorLinkUrl`, the sponsor redirect) and in app.js. `town.keyPrefix` (Victoria `vic361`; another town its slug, never `vic361`) starts every key the server hands an outside account: Stripe lookup keys, product metadata (`<prefix>_package`) and idempotency keys, Resend idempotency keys (newsletter batches, welcome, reminders, sponsor and submission mail) and Tremendous `external_id`s, so two towns on one account can't collide. Browser storage keys (`vic361-theme`, `vic361_admin_pat`…) stay as they are: each town has its own origin. Every town's checkout sessions (and their payment intents and subscriptions) carry `metadata.town`, Victoria's (`victoria`) too since Oct 2026; her older ones carry none, and untagged still means Victoria. A one-time payment also sets `payment_intent_data.statement_descriptor_suffix` from `statementSuffix(town.siteName)` ("VIC 361", "SHOALS": at most 10 characters, so the shared account's prefix fits Stripe's 22), so the card statement names the town. The webhook skips `checkout.session.*` and `customer.subscription.*` events tagged for another town (untagged = Victoria); invoices, charges and fraud warnings only ever match the town's own orders, and a fraud warning that matches none alerts only on Victoria. Inbound email (`server/inbound.js` `isForTown`): another town posts only mail sent (to or cc) to its own domain or a subdomain; Victoria posts everything except mail addressed only to another town's domain (`otherTownDomains()`, read from `towns/*/town.json`), so a Bcc or forward still reaches it. A town's data files come from `townPaths()` (`server/town.js`): Victoria's stay at the repo root (`candidates.json`, `collection_metadata.json`, `venues.json`…) and in `docs/` (`events.json`, `social/latest/`); another town's are under `towns/<slug>/`, its public ones in `towns/<slug>/public/`. The server reads them from there, `/api/config` gives the admin `github_events_path` and `github_candidates_path` for its GitHub reads and publishes, and `tests/town_paths.test.js` pins Victoria's. The Python twin is `town.py` `town_paths()` (plus `repo_path(key)`): the collector's `--candidates` and `--local-dir` defaults, the social kit's output and venues, `social_post.py`'s kit, `review_submissions.py`'s venues and `send_digest.py`'s candidates come from it. Workflows that touch these files run a `Town paths` step first (`python3 town.py paths >> "$GITHUB_ENV"`, giving `TOWN_DIR`, `TOWN_CANDIDATES`, `TOWN_EVENTS`, `TOWN_SOCIAL`…) and use those variables in their arguments and `git add`s; for Victoria they are exactly the old paths. `test_workflows.py` fails if a step reads `TOWN_*` before that step. The town workflows (collect, event check, digest, newsletter, social kit, submission review, uptime, Meta ads) take a `town` dispatch input (default `victoria`) and set `env: TOWN: ${{ inputs.town || 'victoria' }}`; scheduled runs are Victoria's. Another town's concurrency groups get a `-<slug>` suffix and its cache keys a `<slug>-` prefix (so Victoria's `review-state-` restore prefix can't match them); for Victoria both are empty, so its groups and keys are unchanged. Workflows the server starts (the scheduler's daily jobs, the admin's Run collect) get `townInputs()`: another town adds `town: <slug>`, Victoria's dispatches carry no `town` input, exactly as before. Jobs on Railway (`server/jobs.js`, `scripts/jobs_worker.py`, JOBS_ON_RAILWAY.md, RAILWAY.md "Jobs on Railway"): with `JOBS_ON_RAILWAY=1` and `JOBS_SECRET` (32+) every worker job of the scheduler (collect, event check, submission review, social kit, ads report, digest) and Pull Now queue a job in the town's database (`job_queue`, created on first use like `town_meta`); nothing is ever dispatched to GitHub, and a jobs town ignores `GITHUB_TOKEN` (`townWorkflowsReady()` is false; no `docs/events.json` commit, no candidates from GitHub); the town's jobs service (`Dockerfile.jobs`) claims it over `POST /api/jobs/claim`, runs the same script and `POST /api/jobs/:id/finish`es it, and the site says "Collect done" or alerts the failure with the log's tail. A collect `PUT`s its collection metadata, enrichment cache and candidates (last; it publishes at once) to `/api/jobs/files/:name` (`town_files`); `readCandidates()` and the Sources tab use that copy when it's newer than the bundled file. A run past its limit (`JOB_KINDS`) is failed, queued once more (`-retry`) and alerted; the hourly check alerts when the worker hasn't asked for work for 30 minutes. Every route answers 404 without the flag and secret. The social kit (JOBS_ON_RAILWAY.md 2b, Victoria's too since phase 5) is a worker job for every town (`canRunOnWorker`): `job_social_kit` builds the day's kits with `social_kit.py` (Monday week/weekend/today, Thursday weekend/today, else today, in the town's timezone), `PUT`s each file to `/api/jobs/social/:build/:name` and publishes the build (`POST .../publish`, refused unless every slide in its `kit.json` is there), which the site keeps in `social_files` (made on first use, only the latest build kept, 20 MB a file, 60 MB a kit) and serves at `/social/latest/<name>` (anything else under `/social` stays a 404, so Victoria's files never show on another domain). Victoria's `/social/latest/<name>` comes from her database once her worker has published a kit; before that, without jobs on, or when her database can't answer, the git copy in `docs/social/latest/` is served, and her `social_posted` file is read merged over git's `docs/social/latest/posted.json` (`createJobs` `seeds`, `mergePosted`) so the switch day never posts twice. With `SOCIAL_AUTOPOST=1` on the jobs service it then runs `social_post.main(..., on_save=)` in-process with the town's `META_*` settings, saving `posted.json` to the town file `social_posted` before each publish call (`StateNotSaved` stops the post when that save fails), so a retry or restart never posts twice; switched on with Meta settings that aren't the town's own fails the job. The slides use the town's own `logo-512.png`, `skyline.svg` (`town.py` `town_asset`, never Victoria's copy) and its `BRAND.md` palette (`brand_palette`); Victoria's colors and assets are exactly as before. ## Collector quality

`merge_events` in `collect_events.py` is the single quality gate: it drops scraped events outside Victoria County (`out_of_area_reason`; local YAML and Google Sheet rows, `HAND_SOURCES`, are trusted and marked `curated`), moves street addresses out of the venue field and blanks placeholder venues like "Victoria" (with or without a ZIP: "Victoria, TX 77901") or "Restaurant of the Week" (`clean_venue`; a street with no `venues.json` match leaves the venue blank so the site shows the address), blanks a nightlife time that can't be right ("Comedy Night" at 10 AM), and fuzzy-dedupes per day (`is_same_event`: also ignores organiser prefixes and city words when both name one place, and treats Theatre Victoria as the Welder Center; AI-written post names of one festival day, like "Tejas Fest 2026 (Day 1)", "Tejasfest (VIP shift)" and "Tejas Fest - Main Stage", merge once the qualifiers are stripped, with a vague venue such as "Downtown Victoria" or "Main Stage" counting as unknown: `_same_festival`; one weekly special posted on FB and IG, like "Taco Tuesday - Birria Tacos" and "$2 Birria Taco Night", merges at one place when neither gives a time and the shared words, plurals folded, include a distinctive one, never just "Bingo" or "Trivia"), keeping the record from the higher-ranked source in `SOURCE_RANK` and filling gaps from the other. The merged name is the whole one over a cut-off copy, an official source's over an AI-written one, else the shorter. One listing each source words differently ("Wednesday Market", "Midweek Market" and "Victoria Farmers' Market", all 9 AM at the market) merges through `_same_slot`: the same venue name (not just a shared street address; never a vague venue), date and known start minute, at least one name AI-written, hand-entered or generic, and either a shared distinctive word (film/screening count as movie; weak words like "society" or "halloween" don't) or a generic name for the night's act ("Live Music", "Karaoke", "Trivia") of the same kind as anything generic in the other; two hand-entered events never merge this way. Auto-publish's `sameSlot` (`server/autopublish.js`) mirrors it for copies already live. A hand-entered event's place always wins too (`_merge_pair`: its venue and address, the other copy's address only filling a gap at the same place), and in `_tidy_festival` a venue the festival's name starts with ("Walker Ranch" in "Walker Ranch Fall Festival") counts as a real place, not the festival's own name; before, a post filed under the account that shared it (L&C Beauty Studio) took the ranch's place. A hand-entered event's price always wins: the AI review never changes `free` on a `curated`/`HAND_SOURCES` event (its free icon follows its own flag) and writes its description only when it's under `CURATED_REWRITE_BELOW_CHARS`, and `_merge_pair` keeps the hand-entered copy's `free`. Religious words only count in the name; descriptions need clear phrases ("worship service"). `safe_fetch` tags every event with `_source`, which the admin shows as a pill (and shows a scraper's note, like city calendar pages skipped by its cap). The city calendar reads every listing's full `eventTitle` heading, and when the window runs into next month it also fetches that range (`Calendar.aspx?startDate=…&enddate=…&CID=0`; the default view stops at month end; a failed range marks it partial). The Chamber's date comes from the detail page's "Date and Time" block ("Wednesday Oct 14, 2026"), else the URL slug, never another date on the page; more than `CHAMBER_MAX_PAGES` links marks it partial; Theatre Victoria reads the season cards' posters (shows play at the Welder Center; no 7:30 PM on Sundays) and, like Moonshine, runs with `expect_events=False`: between shows it notes "no show in the window", and warns only when the fetch fails or the page has no dated shows. A post from an organizer account (`venues.json` category matching `_NON_PLACE_CATEGORY`: promoter, aggregator, festival, media) with no venue named gets a blank venue, never the account (`_post_event_venue`). FB events must name Victoria plus a whole-word TX/Texas or a 77xxx ZIP (`_fb_location_is_victoria_tx`). Tests: `test_quality.py`, `test_event_data.py`, `test_collector_round6.py`. Hand-added one-time events in `local_events.yaml` are collected out to `LOCAL_HORIZON_DAYS` (90) instead of the 14-day window, so festivals weeks away reach the site, guides, sitemap and "Coming up"; recurring YAML entries and every scraper stay in the window, and the AI review skips events past the window (they're hand-written; reviewing them every run would add minutes) and past days from the Monday backfill. A `local_events.yaml` that doesn't parse (or isn't a mapping) fails the collect before `candidates.json` is written, so the old candidates stay and the failure alert fires; one malformed entry is skipped with a warning. A recurring `day:` can be a plural, an abbreviation or a list ("Fridays", "thur", "Fri & Sat", `[friday, saturday]`; `recurring_days`); anything else is skipped with a warning. Every YAML event is published with `curated: true`: `scripts/sweep_events.py` then skips its religious/out-of-area/wrong-day/non-event checks for it (a person already decided; duplicates and odd times are still flagged), and auto-publish's "looks broken" guard counts only scraped events in the next 14 days, so far-ahead hand-added events can't make a failed scrape look healthy. Optional YAML fields ride along to the site: `big: true` (a highlight for "Coming up") and `town:` (a nearby town for the few big events outside Victoria County, which only hand-added events may be). Thin events (no time or link, or a description under 70 characters) get their blanks filled by `enrich_thin_events`: Gemini with Google Search, accepting only answers whose source page is on a site Gemini cited (links must also load and name the event; a time or address also needs its link or source page to load and name the event, otherwise only the description is taken), never overwriting a set field; events with no link first (every event should carry a source link when one exists, so a hand-added event needs only a name, date and venue), then soonest first, `ENRICH_MAX_PER_RUN` (48) per run, results cached per date, name and venue in `enrichment_cache.json` (committed by `weekly-collect.yml`; misses retried after 7 days; `ENRICH_ENABLED=0` turns it off). ## Traffic stats

`server/analytics.js` powers the admin **Traffic** tab. People are counted from a `docs/track.js` beacon (`POST /api/track`: page views and sponsor/event/subscribe clicks; skipped in a browser signed into the admin). A page view is sent only once the visitor engages (scroll, tap, click or key) or the page has been visible for 5 seconds, so JS-running bots and instant bounces aren't counted; counts dropped when this started on 2026-10-05. search and AI crawlers are counted server-side by user agent (HTML pages plus `/events.json` and `/llms.txt`), at most 30 a minute per client address and 300 a minute overall (`crawlerMiddleware`; the user agent is unverified, so an uncapped loop could fill the database). AI bots are tagged `ask` (an assistant fetched the page to answer someone, e.g. ChatGPT-User), `search` or `training`; the summary's `ai` block reports people sent by AI referrers (or `utm_source`, which ChatGPT adds when there's no referrer) and those three counts. **Ad views:** paid placements carry `data-ad="<order id>"` (the weekly sponsor block and paid Vic's Picks, never editor's picks; `adAttr` in `server/seo.js`, the same in `docs/app.js`; `applyPlacements` puts `sponsor.order` and each paid pick's `sponsor_order` on the payload at read time, `/events.json` keeps them for app.js, Save & Publish strips `sponsor_order`). `track.js` sends one `{kind:'impression', ad}` per ad per page load once at least half of it has been on screen for 1 s with the tab in front (IntersectionObserver; no IO, no impressions), and clicks inside a `[data-ad]` carry `ad`; `beaconRow` takes only ids matching `AD_ID` and skips bots like views, and rows store it in the `ad` column. `/api/track` counts at most 20 impressions and 5 clicks per client address per ad (or per sponsor/event link) per day (`adBeaconAllowed`), so a script can't pad a sponsor report. The Traffic tab ignores impressions. Rows go to the `traffic` table (Postgres, ~400 days kept) with a daily salted visitor hash and no IPs or cookies. `GET /api/admin/traffic?days=N` returns the summary (Postgres groups rows in SQL and `summarize` weighs each by its count `n`, so a year's range stays cheap).

**Sources are people, not page views (Oct 2026).** `sources` (Traffic tab "Where visitors come from", and the activity report) counts each visitor once per day by the outside source that brought them (`visitorSources`): later pages they reach by moving around the site send a same-site referrer, read `Direct`, and never beat an outside source; two outside sources in a day go to the first (`first_at`, the group's earliest `ts`). `source_views` keeps the old per-view counts (the shares box reads "views from shared links" from it). **Newsletter visits:** a view tagged `utm_source=newsletter` is `Newsletter` whatever the referrer (Gmail's link redirect sends google.com, webmail its own host; before Oct 2026 those read Google or Other sites), webmail hosts without the tag (mail.google.com, the Gmail app, Outlook, Yahoo Mail) are Newsletter before the Google rule, and the link's `utm_campaign` (`weekly-<Monday>`, `weekend-<Thursday>`, `welcome`; `EMAIL_CAMPAIGN`) is kept in the view's `ref_host`, so the issue report credits the right issue. **Event clicks:** `event_click` is a tap out to the event's own link (the "See event details" button, a list item that links out); a tap from a list to the event's page here is `event_open` (`docs/track.js`, both from `.event-entry`; the 404 page's own buttons in `.page-actions` aren't event clicks). Rows from before the split (an `event_click` to one of our own pages) are read as `event_open` by `summarize` and `activitySummary` (`isOutbound`). Compare towns on `event_link_clickers_per_100_visitors`, not raw counts.

**Shares.** Every share button (`[data-share-url]`, `docs/track.js`) shares or copies the link with `?s=sh`, and counts a share (`share_native`, `share_from_list`) only once the share sheet reports it sent or the link is copied, not when the sheet is opened and closed. A page opened from such a link sends its view with `via: 'share'`, which `beaconRow` records as the source `Shared link` (`SHARED_LINK`, whatever app it was opened in), and the tag is removed from the address bar so a reload or copied URL doesn't count again. Vic's Pick reports add "Visits from shares" (`pickStats` `share_visits`/`share_people`). Admin Traffic → **Event stats** (`GET /api/admin/event-stats?week=<Monday>`, default last week; `eventWeekStats` in `server/sponsors.js`) lists every event dated that week, counting each from 7 days before its date through its date (`LEAD_IN_DAYS`), with page views (its own link taps and shares only, not those of the other events listed on its page), link taps, calendar adds, shares and visits from shares, plus the week's newsletter reach, and **Copy pitch** copies an email offering the venue a Vic's Pick.

**Meta ads.** Pages reached from links carrying a subscriber token (`/subscribe/confirm`, `/unsubscribe`) render with `layout({ pixel: false })`, which also leaves Google Analytics off, and the pixel script itself skips any URL with `token=`: both tools report page URLs to a third party. Everywhere else GA gets `page_location` as origin + path plus only `utm_*`/`gclid` (`GA_SNIPPET` in `server/seo.js`, copied into `docs/index.html` and `docs/submit.html`; a test keeps them identical). `/privacy` (`renderPrivacyPage` in `server/legal.js`, linked from every footer) discloses the pixel, Google Analytics (only for a town with a GA ID) and our own stats, as Meta's terms require. `/pixel.js` (`server/metaPixel.js`) loads the Meta Pixel on public pages when `META_PIXEL_ID` is set and is an empty script otherwise; it skips the same admin/preview/social-kit visits as `track.js`, and any browser sending Global Privacy Control (`navigator.globalPrivacyControl === true`; the privacy page promises this). It reports `PageView`, and `track.js` reports `Lead` when a newsletter signup succeeds and `/api/subscribe` answers `lead: true` (a checked signup with no referral code, which joins right away; not one waiting on its Confirm tap, nor a honeypot hit; the flag depends only on the request, so it never tells who's subscribed). Ad links should end in `?utm_source={{site_source_name}}&utm_medium=paid&utm_campaign={{campaign.name}}`: a tap on an ad has the same facebook.com/instagram.com referrer as a free post, so `utm_medium=paid` is what puts it under **Meta ads** in the Traffic tab (`paidSource` in `server/analytics.js`; other paid sources show as **Other ads**).

## Event scoring and the daily limit

`server/scoring.js`: each day shows its best `DAY_MAX` events (15 Mon–Thu, 20 Fri–Sun). `getPublicPayload` runs `capDays`, which scores every event (0–100, `scoreEvent`) and marks the rest of a full day `overflow`. Day lists use only events that made the cut (`shownPayload` / `shown`): `/events.json` (so the homepage app and social kit; `/events.json?all=1` is every public event with `overflow` flagged, for the event check and submission review, which must see everything that's live), the server homepage, `/today`, `/tonight`, `/this-weekend`, `/next-week` and other non-`upcoming` hub pages, `llms.txt` and the newsletter. Event pages, category guides (`range: 'upcoming'`), seasonal and venue guides and the sitemap keep every event. Site lists stay in time order, Vic's Picks included (`sortEvents`); the score only decides what's in. Always in: `featured` (Vic's Picks, sponsored) and events the admin chose to show anyway (`POST /api/admin/keep-event`, stored as the published payload's `kept` key list; the admin's event list shows "Dropped · score N" with a Show anyway / Undo button). Score signals: the AI review's `appeal` (1–5, `ai_review`), `big`, festival/concert/parade names, weekly repeats (`recurring`; `favorite: true` in the YAML keeps a staple's spot), niche (club, meeting, class...) and store-promo wording, family/free, missing time/place/description, a link, `sources` (how many sources listed it), hand-added (`curated`) and approved submissions (`submitted`, set by auto-publish), popular (tier HIGH) venues, and small nearby-town events. `recurring` is sticky on live events (a post can say "every Tuesday" one run and "this Tuesday" the next). The event check sends at most 10 hides per run (the server's limit), day-list events first. A full day also keeps variety: at most 2 per venue and 3 of a kind (trunk-or-treats, karaoke, bingo...) unless a score is 80+, then fills leftover room by score. `score`, `overflow` and `keep` are never stored on events (stripped from `/events.json` and from Save & Publish). Editor's picks (`pickDays`, after the cap): a day's can't-miss events get the Vic's Pick badge on merit, up to 2 Mon–Thu and 3 Fri–Sun counting paid picks first (a paid one takes an editor's spot; paid capacity is counted from orders in `sponsors.js`, never from these). Score 70+ to be picked; a day with none that strong still gets 1 (2 on weekends) of its best if they reach 65. Only one-time Victoria events, each picked once (first day), one per venue. On the site (`sortEvents`, the same in `docs/app.js`) and in the newsletter's day lists a day is in time order, and `pickRank` (paid picks, then editor's picks, then the rest) only breaks a tie at the same time and leads the hub-page intro's "including …" names and the event page's "Also that day" pick of six; the social kit's day lists and cover and the newsletter's highlights still lead with picks; only paid picks count for the social kit's Thursday "today" post. They're `featured` plus `editor_pick`, computed on read: kept out of "Coming up", described as editors' picks in `llms.txt`, labeled "Vic's Pick (auto)" in the admin, and stripped (with their `featured`) from Save & Publish. Tests: `tests/scoring.test.js`, `test_scoring_hints.py`.

## Auto-publish

`server/autopublish.js`: each collect hands its candidates to the site (`PUT /api/jobs/files/candidates`), which publishes at once; on boot too, in production (`RAILWAY_ENVIRONMENT_NAME=production`, unless `AUTO_PUBLISH=0`) the upcoming candidates plus approved submissions are published to the store. Upcoming events already published are kept; one it added takes the collector's newer copy of itself (time, venue, address, link, description, icons; the name only when the live one was cut off), unless the admin edited it, it's an approved submission or featured, and a hidden one keeps its name and venue (its key); `auto_publish.keys` follows the new key (`AUTO_PUBLISH_RULES` 3). An event it added is taken down only after two collector runs in a row miss it (`auto_publish.missing`, counted once per `last_updated`), each with all of its sources `ok` in `candidates.json`'s `sources` map (`partial` doesn't count: an AllEvents page came back full (`ALLEVENTS_PAGE_CAP`; the "all" page is a capped trending list) or failed, a library week, city calendar or chamber detail page, or J Welch date page failed, one FB-events actor was down, or an FB-events/Eventbrite search hit its result cap, via `_mark_partial`), and never when it came from FB/IG posts (`NEVER_RETIRE_SOURCES`; window-limited; each key's sources are kept in `auto_publish.sources`; a Gemini-only event retires like any other, since Gemini's answer was its only evidence), nor when the run looks broken. Approved submissions (also in `keys`) count as found while their row is approved, since the collector never lists them (read with `store.list({ status: 'approved', fromDate: today })`, which has no row cap: the admin list's newest-500 cap once dropped an approval made long before its date, and it was retired as missing; `retryLive`, the paid pick reminders and the admin picker read it the same way); when the approved list can't be read, nothing is retired. Events it added that the admin later removed are remembered (`auto_publish` in the published payload, hidden from `/events.json`) and not re-added, nor is a collector copy that `sameEvent` matches with a removed or hidden key (the AI's names drift run to run; an approved submission is never blocked this way). A collector copy that only `sameSlot` matches with a live event folds into it without refreshing it. An approved submission that merged into a listed event under another name is recorded in `auto_publish.aliases` (submission key → live key); when that live event is removed, the alias counts as removed too, so the submission's copy doesn't come back. `POST /api/admin/auto-publish` forces a run. The collector drops non-events (`non_event_reason`: job/internship posts, booking ads, awareness-day posts) and decodes HTML entities; with `OPENAI_API_KEY`, the AI review also returns `keep: false` for non-events. `weekly-collect.yml` runs Sunday and Wednesday. Whether a published event is still upcoming is decided on its edited copy (the `event_edits` overlay), so an event the admin re-dated to later stays live past its stored date without a Save & Publish; when the edits can't be read, past events stay that run too. ## Growth (admin)

`server/growth.js` is Admin → Growth, and its two goal bars are also at the top of Home. `GET /api/admin/growth?days=7|30|90` (admin only) returns:

Anything the admin has edited or decided is left alone; at most 20 per call; no AI answer means it waits for the next run. When submissions wait and the AI can't answer at all (`OPENAI_API_KEY` empty, the key rejected with 401/403, `insufficient_quota`, the model gone, or every call in the run failing), the rule decisions still go through, the remaining calls are skipped, and the run exits 1 so the workflow's Slack step fires; it does that once, then every 6 hours while the outage lasts (`ai_down_alert`, `ALERT_EVERY_S`; the last alert time is kept in the Actions cache, `.review-state/ai-alert.json`), and a run that gets an answer clears it. A single timeout, 5xx or rate limit still just waits. Secret: `SUBMISSION_REVIEW_SECRET`, falling back to `EVENT_CHECK_SECRET`, then `NEWSLETTER_CRON_SECRET` (same in Railway and GitHub). Free submissions the review would approve are flagged "passed the review; ready for your OK" (with the suggested tidy-up in the notes) unless `SUBMISSION_AUTOAPPROVE=1` in Railway; paid picks go live on their own either way. The "we got it" receipt has a fixed subject and none of the submitter's free text beyond a shortened name, and goes to one address at most 3 times a day (the form takes any address). Upgrade links (thank-you card and emails) are `/advertise/checkout?package=featured&from=<submission id>`; the checkout fills the event and contact in on the server, so no contact details are in URLs that analytics see (the checkout ignores `email`/`business` in the query). Approved submissions never publish the submitter's name or phone: auto-publish, the admin candidate merge and the public read path all drop `submitter_*` fields. Tests: `test_review_submissions.py`, `tests/submission_review.test.js`.

## Event check

`scripts/sweep_events.py` (the jobs worker's `event-check` job) looks over the live `/events.json` for the next 14 days after each successful collect and Monday 6:43 AM and Thursday 6:00 AM town time, an hour before each issue. Rules first, free: the collector's `is_same_event`, `out_of_area_reason` and `non_event_reason` run again over the published list (hand-added events and ones published before a rule existed), plus a weekday in the name that doesn't match the date, starts before 6 AM, and a nightlife name or bar venue at 6–11 AM (reported only). Then one OpenAI call (`OPENAI_MODEL`, default gpt-5-mini) over the whole list for what per-event checks can't see, like the same event at two venues; skipped without `OPENAI_API_KEY`. Rule findings it's sure about (church/worship events by name or venue, non-events, exact duplicates, the library's copy of a program the city calendar lists at its real place with the same hours, and a cut-off name when the same event's full listing is at the same place that day: its name holds every word left in the cut-off one, or after an "Organizer — " prefix, or it starts at the same known time and shares a distinctive word; another event at the venue isn't enough, and a vague venue ("Victoria", "Downtown") never counts as a place; `AUTO_HIDE`) it hides through `POST /api/event-check/hide` (`server/eventcheck.js`, `X-Cron-Secret` = `EVENT_CHECK_SECRET`, falling back to `NEWSLETTER_CRON_SECRET`; at most 25 per run, only live upcoming events). A paid Vic's Pick (`featured` and not `editor_pick`) is never hidden for any rule, here and in the endpoint (skipped with `why: 'paid-pick'`; the endpoint applies the placements itself with a strict sponsor-order read, `sponsors.apply(..., { strict: true })`, since paid picks are `featured` only at read time, and answers 503 `orders-unavailable`, hiding nothing, when the orders can't be read): it stays in the report and goes to Slack sales (`SLACK_SALES_WEBHOOK_URL`, else alerts), since a sold, approved listing needs a person. An approved community submission (`submitted: true`) is never auto-hidden either (nor picked as the copy to hide for a duplicate): the owner approved it by hand, often over the same rule, so it's only reported. On any run, duplicates are only hidden when exact (same normalized name, venue and start) and neither copy is featured; the copy with less detail goes. A bar's standing "Live Music at X" (or "Karaoke at X") is flagged as a duplicate when that night's act is listed at the same place with overlapping times (`_placeholder_for`). Hiding never deletes: the published payload gains a `hidden` entry, matched by the event's original key (date|name|venue before the edits overlay), not its page URL, so slug renumbering and admin renames can't move or undo it; entries are kept 400 days so past pages stay hidden, and `getPublicPayload` (and the bundled fallback) leave those events out (site, `/events.json`, newsletter, social kit, sitemap, event pages); auto-publish and Save & Publish carry it forward. The admin Home tab lists hidden events with Restore, which also records the original key in `hidden_restored` so the check never hides it again; the Events tab labels them "Hidden by check". **Before the send** (the scheduled Monday and Thursday runs; the worker passes `--before-send` for any slot that isn't `after-collect-*`), nobody may have read the flags, so what is still likely wrong in the coming 7 days comes down (`before_send_picks`): fuzzy and placeholder duplicates the rules found, the AI's duplicates on the same day at the same place or sharing a distinctive name word, wrong days, non-events, church events, out-of-area listings, and starts before 6 AM. For a pair it hides the placeholder, else not the hand-entered (curated) copy, else the copy fewer sources listed, without a time, with the shorter name, with less detail (`_loser`). Never a paid pick or an approved submission, and never anything Restored. The AI's odd times and "other" findings, and the rules' "early for this kind of event", stay flags. After a collect, those items are flagged with "hidden before the next issue unless fixed". The newsletter also drops same-day duplicates at one street address and placeholders itself (`server/newsletter.js` `issueDays`), in case a check didn't run. One short Slack line to the activity channel (`SLACK_ACTIVITY_WEBHOOK_URL`, else `SLACK_WEBHOOK_URL`, which on the jobs services reaches sales): how many it hid and how many of each kind to look at. The full list (what it hid, then each event to look at, links as plain names, cut at `MAX_HQ_TEXT`) goes to the owner inbox through `/api/ops/report` with `fyi: true`, saved as an fyi activity item and never posted (`server/opsReport.js`); the Railway log keeps all of it. Without the secret it only reports. After a collect it first waits (`--wait-for candidates.json`, up to 15 min) until the live `collected_at` (the candidates.json last_updated auto-publish last put live) is at or after the candidates' `last_updated`; only for a feed without `collected_at` does it fall back to a newer list that holds some of the upcoming candidates it lacked at the start (a newer `last_updated` alone could be a submission approval during the deploy). Counting keys alone raised false alerts when auto-publish beat the first fetch, since hidden or merged candidates never show; if they never show (usually no Railway deploy) it sends a Slack alert (alerts channel) and checks what's there. Event names, venues and AI text in the Slack message are escaped (`slack_notify.escape`: `&`, `<`, `>`; a `|` in link text becomes `¦`). Tests: `test_sweep_events.py`, `tests/eventcheck.test.js`.

## Scheduler

The always-on server is the clock (`server/scheduler.js`, production only, `SCHEDULER=0` turns it off), in the town's timezone, DST-correct. Worker jobs (a `kind` in `JOBS`, one of `server/jobs.js` `JOB_KINDS`) are queued for the town's jobs worker: Sunday and Wednesday 3:23 PM the collect (`weekly-collect`, `weekly-collect-midweek`, until 9 PM), Monday 6:43 AM and Thursday 6:00 AM the event check (`event-check`, `event-check-weekend`; also queued after every collect), daily 8:37 AM the ads report (`meta-ads`), 8:47 AM the social kit (`social-kit`), Sunday 9:00 PM the digest (`weekly-digest`, kind `digest`), every 15 minutes the submission review. In-process: Monday 7:43 AM the newsletter (`scheduledSend`, retried after 5, 15 and 30 minutes, then an alert), Thursday 7:00 AM the weekend issue (`newsletter-weekend`, `scheduledSend('weekend')`), daily 9:00 AM `sponsors.sendSponsorReports(now)` when it exists, daily 3:17 AM `privacy-purge` (`server/privacy.js`: clears the IP address and user agent on submissions older than 12 months, deletes contact messages older than 24 months), and hourly a site check (database, at least 10 upcoming events, a collect within 8 days, and each Sunday/Wednesday collect in by 3 hours after its slot (`missedCollect`, against `auto_publish.from`); alerts once a day while it lasts, a note when it clears; alerts go to Slack #alerts and, as urgent, the owner inbox HQ reads). Each daily/weekly job is claimed once per slot in `scheduler_runs` (one SQL statement, so a restart or overlapping deploy containers can't double-fire); a job missed while the server was down runs later the same day; a worker job that can't be queued is retried after 2 and 5 minutes, then alerted. Nothing is started on GitHub: without jobs on Railway (`JOBS_ON_RAILWAY=1` and `JOBS_SECRET`) the worker jobs don't run at all, and the setup checklist says so. Each newsletter slot records what it did (`scheduler_runs.detail`, in `/api/hq/summary` `newsletter_runs`). The one newsletter switch is the Railway variable `NEWSLETTER_AUTOSEND` (on unless `0`); `POST /api/newsletter/cron` (`NEWSLETTER_CRON_SECRET`) sends by hand and honors it for runs marked `X-Cron-Scheduled: 1`. Tests: `tests/scheduler.test.js`, `tests/jobs.test.js`, `tests/ops.test.js`.

`/api/health?deep=1` also asks the database and answers 503 when it's down or slow, or (`no-database`) when production (`RAILWAY_ENVIRONMENT_NAME=production`) runs on the file store because `DATABASE_URL` is missing; that also alerts at boot and from the hourly check. Plain `/api/health` stays process-only so a database blip can't fail a deploy. When a read of the published list fails, the site serves the last list it read (`lastGood`, with the last edits overlay), and only falls back to the old bundled `docs/events.json` when it never read the store since boot; both alert (`db-read`) and pages built from a fallback are sent `no-store`. `PgStore` has a circuit breaker (`breakerPool` in `server/db.js`): after a connection error or timeout (no SQLSTATE, or class 08/53/57P; not a statement timeout, 57014, unless it's the probe, and not a checkout timeout while every pool client is busy) every query fails at once for 30 s, then one probe goes through, so a hung database costs one wait, not 5 s per query per request. `ready()` asks `information_schema.columns` once and runs `ALTER TABLE ... ADD COLUMN` only for a missing column: the ALTER takes an ACCESS EXCLUSIVE lock even when the column exists, which queued behind a long traffic report on every boot. The hourly check also re-runs auto-publish (not forced, so a no-op once the latest collect is live), which catches up a boot publish a database blip made fail. `uptime.yml` (`scripts/uptime_check.py`) asks GitHub for every 5 minutes, but GitHub's cron is best-effort and on this repo is often hours late (runs land every 3 to 9 hours), so it is only a backup. The real-time check is an external monitor (UptimeRobot or similar, set up by the owner) polling `/api/health?deep=1` every few minutes and posting to the Slack alerts webhook; it depends on neither GitHub nor the Railway process. Its daily stale check has its own cron (`17 15 * * *`). The server's own hourly check (`server/scheduler.js`) also alerts when fewer than 10 upcoming events are live or the last collect is over 8 days old (`collected_at`). It also alerts (`subscribers`) when active subscribers fall below 60% of the last `newsletter_sends` row's recipients (on a list of 20 or more; at 0 on any list), and `ready()` alerts `db-fresh` in production when it had to create the `subscribers` or `sponsor_orders` table (a new, empty database); see Backups.


`server/slack.js` posts to a Slack incoming webhook (`SLACK_WEBHOOK_URL`, same setup as austincommercialsites.com). No-op when unset. Server pings: new event submission, sponsor paid, venue partner cancelled or payment failing, newsletter sent (or partly failed / skipped because nothing was published), and alerts for 500s (keyed on the error message; 4xx client errors like malformed JSON or a bad `%` escape answer with their status and never alert), Stripe checkout or webhook failures, crashes, boot failures, a database unreachable at boot (the server still starts: pages fall back to the bundled `docs/events.json` and the store retries on the next query; the pg pool has an `error` listener, a 5 s connect timeout and 15 s query/statement timeouts) and a flood of failed admin sign-ins. Alerts are de-duplicated per key for 15 minutes. Slack posts and the Turnstile check time out after 8 s, so a hung Slack or Cloudflare can't freeze a form. Five channels, each optional and falling back to `SLACK_WEBHOOK_URL`: `SLACK_SALES_WEBHOOK_URL` (refunds, disputes, failed payments, sponsor and pick reports, a paid pick marked rejected), `SLACK_ACTIVITY_WEBHOOK_URL` (submission review, auto-publish, newsletter sent), `SLACK_ALERTS_WEBHOOK_URL` (every `alert()`), `SLACK_HYPE_WEBHOOK_URL` (wins only: new subscribers, new paid sponsors and Vic's Picks; falls back to sales) and `SLACK_INBOX_WEBHOOK_URL` (people talking to us: email replies to news@, contact-form messages, new event submissions, and each "Replied to" we send; falls back to activity). Pass `channel` to `slack.notify` for new pings. A refused webhook (HTTP 403/404/410, or `no_service`, `channel_is_archived` and the like: archived channel, removed app) is remembered per channel by `server/slack.js` (`slack.refused()`), fails the Slack item in the admin setup checklist and is a problem in the hourly site check; it clears on the next post that goes through. GitHub Actions use `scripts/slack_notify.py`, which exits 2 with an `::error::` on a refused webhook (so the run goes red and GitHub emails the owner) and 0 on a hiccup (timeout, 5xx); failure steps read `SLACK_ALERTS_WEBHOOK_URL`, the collect-done and outreach steps read `SLACK_ACTIVITY_WEBHOOK_URL`, both falling back to `SLACK_WEBHOOK_URL`: weekly collect done (candidate count plus the collector's warnings from `collection_metadata.json`, also sent to the alerts channel) or failed, social kit / newsletter / digest failures, tests failing on main, and `uptime.yml` (site check every 5 minutes: alerts once when down, hourly while down, once when back; also a phone push when the `NTFY_TOPIC` secret is set; daily stale-feed check). Async route handlers are wrapped (`catchAsyncRoutes` in `server/index.js`) so a rejected store call answers 500 instead of hanging on Express 4. Auto-publish alerts when a run finds far fewer events than the last (nothing retired), when nothing upcoming is published, and when it can't run on boot.

## Backups

Postgres on Railway holds the only copy of subscribers, sponsor orders, submissions, admin edits, the hidden/kept/rejected state and the event archive; events refill from `candidates.json`, nothing else does. The admin's Email tab can download the subscriber list as CSV (`GET /api/admin/subscribers.csv`), and RAILWAY.md "Backups and data exports" has an encrypted `pg_dump` recipe (never a GitHub Actions artifact: the repo is public). The repo has no backup job, so **the owner must turn on Railway's scheduled Postgres backups** (Railway dashboard → the Postgres service → Backups → enable a daily schedule; keep at least 7 days) and check after a week that backups are listed. **This is per database:** each town has its own `Postgres-<town>` service (Postgres-TheVic361, -Tupelo, -Crane, -Medford, -Shoals and the ones for Lincoln and Virginia Beach), and each needs its own schedule; a new town's database starts with none.

To restore: Postgres service → Backups → pick the latest backup from before the loss → Restore (Railway restores into the service's volume and restarts it). If the service was recreated instead, restore the backup to it, then make sure the app's `DATABASE_URL` references that service, and redeploy the app. Afterwards check admin Home (subscriber count), the Sponsors tab and `/api/health?deep=1`. The server alerts `db-fresh` when production boots on a database without the `subscribers` or `sponsor_orders` table, and the hourly check alerts when active subscribers fall below 60% (`LOSS_SHARE`) of the last issue's recipients (on a list of 20 or more; at 0 on any list), which a wipe, a replaced database or a restore from an old backup all do; either one means restore before the next issue. HQ's summary carries what HQ needs to catch the same from outside: `subscribers.last_send_recipients`, `database` (`first_subscriber_at`, `first_send_at`, `issues_sent`: a database replaced by a newer, emptier one moves these) and `health.database_created` (this process found the tables missing and created them).

**Daily counts on record.** The daily history the summary draws is worked out from today's rows, so a restore or a wipe would quietly redraw it. So each HQ summary build also upserts today's counts (`active`, `pending`, `bounced`, `unsubscribed`) into the town's own `subscriber_counts` table (`store.saveSubscriberCounts(day, counts)`, one row per town-local day, both stores; the file store keeps 400 days). `/api/hq/summary` carries the last 31 as `subscribers.recorded_daily` (oldest first) and `subscribers.drop_since_last_snapshot` (`{ from_day, from, to }`, else null) when today's active count is under 80% of the newest earlier day's with at least 20: a restore from an old backup, a wipe, or a wave of bounces. HQ stores no business data, so the record lives town-side. Tests: `tests/subscriber_history.test.js` (`TEST_DATABASE_URL` adds Postgres).

## Conventions

- **Python:** stdlib + `requests` + `beautifulsoup4` + `pyyaml`. No Django, no FastAPI, no async — keep `collect_events.py` blocking and simple.
- **JavaScript:** ES modules (`"type": "module"` in `package.json`). No TypeScript. No bundler — `docs/*.js` is loaded as-is by the browser.
- **No new dependencies without strong justification.** This is a twice-weekly cron job + a small Express app. Every dependency is a collect-day failure mode.
- **Comments explain *why*, not *what*.** The existing code does this consistently — match it. Documenting the rationale is half the value of every PR.
- **Errors include `.status` when they wrap an HTTP response** (see `server/github.js`) so route handlers can branch on it.
- **Outbound HTTP has a deadline.** Turnstile and Slack use 8 s, Resend (`server/newsletter.js`) and the GitHub API (`server/github.js`, `GITHUB_TIMEOUT_MS`; a timeout throws an Error with `code: 'timeout'` and no `.status`, so the callers' local-file fallbacks run) 15 s. Pass `signal: AbortSignal.timeout(ms)` to any new `fetch`.
- **Secrets only via env vars.** Never commit `.env`. `requirements.txt` caps each package below its next major version; raise a cap deliberately, with a test run.

## Don't-touch list

These files / behaviors are load-bearing and **must not change** in a normal PR. If you genuinely need to change one, call it out explicitly in the PR description and assume it needs human review.

1. **`docs/events.json` outside the admin Save & Publish flow.** The collector (the jobs worker's collect) uses `--candidates-only` for a reason. `test_collect_events_safety.py` pins this.
2. **`candidates.json`** in a feature PR — it's a runtime artifact (Victoria's last committed collect; the worker's copies live in the database).
3. **`collection_metadata.json`** in a feature PR — same, runtime artifact.
4. **`.last-published-digest-*` files** — markers from the decommissioned reply-to-email approval flow. Leave alone.
5. **The collect slots, Sunday and Wednesday 3:23 PM town time (`server/scheduler.js` `JOBS`; `server/sources.js` `next_run_cron` `23 20 * * 0,3`).** `tests/sources.test.js` pins them together. (Moved from `0 23` in Oct 2026 at the owner's request, because GitHub started the on-the-hour evening slot 45–90 min late; keep `server/sources.js` in sync if it ever changes; `tests/sources.test.js` checks they match.)
6. **Job time limits** (`server/jobs.js` `JOB_KINDS.limitMs`, `scripts/jobs_worker.py` `TIMEOUTS`; the collector's own 50-minute budget). Each was sized from real runs. Don't lower without strong reason.
7. **The `--candidates-only` flag default behavior.** Default is *off* (so local runs still write `events.json`); the jobs worker explicitly sets it.
8. **`server/auth.js` — the HMAC-SHA256 token format.** Single algorithm, no `alg` header. Do not switch to a JWT lib.
9. **The legacy `ADMIN_TOKEN` fallback path.** Documented in `index.js`. Keep working.
10. **The browser-side GitHub PAT path in `docs/admin.js`.** Dormant: every town runs jobs on Railway, which never commits to GitHub, so only a service without jobs (a local or staging copy) can reach it; it and `server/github.js` are marked for removal, so leave them alone until that PR. When the server has admin login on, a leftover PAT in localStorage is ignored and an expired session shows the sign-in form. Only a 401 whose `error` is a session error signs the admin out; `/api/admin/trigger-collect` never answers 401 (it queues a collect, or 409 `jobs-not-on`).

## Security notes

- **Cron secrets.** `NEWSLETTER_CRON_SECRET` (send the newsletter), `EVENT_CHECK_SECRET` (hide live events) and `SUBMISSION_REVIEW_SECRET` (approve and publish submissions) are meant to differ. For older setups the server and scripts fall back `SUBMISSION_REVIEW_SECRET` → `EVENT_CHECK_SECRET` → `NEWSLETTER_CRON_SECRET`, so with only one set, that one value grants all three. Keep the fallbacks (removing them would break a running setup), but the admin setup checklist flags a shared value ("Each automation has its own secret").
- **CSP.** `/admin.html` gets `script-src 'self'` plus a hash of its inline theme snippet (computed at boot from the file), because its session token lives in localStorage. Public pages have no `script-src`: they use inline scripts, inline `onload`/`onclick` handlers, GA, the Meta Pixel and Turnstile, so one would need nonces first. Don't add a third-party or inline script to `admin.html` without checking the CSP. The admin CSP is chosen on the decoded, normalized path and again by the file `express.static` serves, so `/admin%2Ehtml` or `/%61dmin.html` can't load the page under the public CSP. `X-Powered-By` is off.
- `trust proxy` is `1` (Railway's edge is the single hop). Don't set it to `true`: Express would then take the client-supplied left-most X-Forwarded-For entry as `req.ip`, and every per-IP rate limit could be bypassed.
- Every rate limiter keys a client address through `ipKey` (IPv6 on its /64; `createRateLimiter` does it for any key that is an IP, so the contact, newsletter and sponsor forms get it too). Admin sign-in: 10 login attempts per client per 15 minutes; wrong legacy `ADMIN_TOKEN` guesses are capped at 20 per client; and 100 failures (logins plus wrong tokens) across all clients send one Slack alert (alert only: blocking everyone would lock the owner out too).
- Submission dates must round-trip (`2026-11-31` is rejected, not rolled to Dec 1), and the public form's submitter email must also pass the newsletter's `normalizeEmail` (Resend refuses `bob@gmail.com.`). The admin edit form's date is `type=date`, and typed-but-unsaved edit fields survive re-renders (`state.drafts`). The public form's start times run from 5:00 AM.
- Anything rendered into HTML attributes must escape quotes (`escHtml` in both `server/seo.js` and `docs/app.js` does). `safeUrl` / `safeHref` reject URLs containing whitespace, quotes or angle brackets.
- Use function replacements (`.replace(x, () => html)`) when inserting rendered content: event text can contain `$'` / `$&`.
- Weekly sponsor holds are saved before the Stripe call, under an in-process lock; a payment for an already-sold week is marked `conflict` and flagged in Slack for a refund. Open (unpaid) holds are capped: one per email, and at most `MAX_HOLDS_PER_CLIENT` (3) per network address (`holdClient`, a salted hash of `ipKey`, stored as the order's `client`), since a mobile carrier or office puts many real buyers behind one address; a checkout past the cap releases that address's oldest hold, so one visitor can't hold every week and pick slot.
- Admin secrets: `ADMIN_SESSION_SECRET` / `ADMIN_TOKEN` under 32 characters (random keys nobody types) fail the required "Admin session secret and token are long enough" setup check and alert Slack on every production boot. `ADMIN_PASSWORD` under 12 is the owner's call: only the recommended "Admin password is 12+ characters" setup item, no alert or log line (the owner chose to keep theirs). Not a boot failure, on purpose: the live site may run on them and refusing to start would take it down.
- Personal data: `server/privacy.js` (daily retention purge, admin "Delete their data" = `POST /api/admin/privacy/forget`, subscriber CSV export). Forgetting an address deletes the subscriber and their opens, contact messages and the submitter fields on their submissions, and masks the address (`j•••@gmail.com`) on sponsor orders and referral rewards; the mailer never sends to a masked address.
- Public forms (submit, newsletter signup and the homepage card, contact, sponsor checkout) carry a hidden spam-trap field, `hp_field` (`server/honeypot.js`, `display:none`). It was `company`, which browsers autofill for business owners, silently dropping real submissions and checkouts; the old name is still honored for cached pages. A hit answers as if it worked, is logged, and Slack's activity channel hears about it at most once a day per form, with the count.
- Cloudflare Turnstile (`TURNSTILE_SITE_KEY` / `TURNSTILE_SECRET_KEY`) protects `/api/submissions`, `/contact`, `/api/subscribe` and `/advertise/checkout`. `docs/turnstile.js` mounts an interaction-only widget on forms marked `data-turnstile` (loaded on first focus; `data-turnstile="fetch"` forms call `vicTurnstile.token(form)`); the server checks `cf-turnstile-response` or `turnstile_token` via `verifyHuman` in `server/index.js`, and when Cloudflare reports the hostname a token was solved on, it must be the site's (apex or www, plus `RAILWAY_PUBLIC_DOMAIN`), so a widget shared with another site can't pass tokens from there. Both off until the keys are set.
